## Story

**As a** lojista-cliente,
**I want** uma página inicial após login que lista as marcas às quais tenho acesso, com logo e botão "Acessar vitrine",
**so that** eu navegue rapidamente entre as coleções disponíveis.

## Acceptance Criteria

1. `/brands` lista todas as marcas onde existe `user_brand_access` ativo para o cliente logado E `published=true`; RLS garante isolamento (a query não filtra explicitamente — a policy `brands_customer_read_published` é suficiente).
2. Cada item exibe: logo da marca (com placeholder SVG quando `logo_url` é null), nome, descrição curta (truncada em 2 linhas), contagem de produtos aprovados.
3. Clique em qualquer card navega para `/brands/{slug}`.
4. Estado vazio amigável quando o cliente não tem marcas: "Você ainda não tem marcas disponíveis. Entre em contato com seu distribuidor."
5. Testes unitários: (a) `P-GBC-1`: `getBrandsForCustomer` retorna array com dados corretos quando usuário tem acesso a marcas; (b) `N-GBC-1`: retorna `[]` quando nenhuma marca está disponível ou ocorre erro.

## Complexity

**Baixo** — 2 pontos

Server Component simples que substitui um placeholder estático. Sem Client Component, sem estado, sem debounce. A lógica mais sutil é o embedded count do Supabase (`.select('..., products(count)')`), mas é uma linha de query PostgREST padrão.

## Business Value

É a página de entrada do cliente após login. Sem ela, o cliente chega em `/brands` e vê apenas o placeholder vazio de Story 1.5, sem como navegar para nenhuma vitrine. Fecha o fluxo cliente: login → lista de marcas → vitrine → pedido.

## Risks

- **Embedded count e RLS:** O count de `products` via join usa a RLS `products_customer_read`; se a política tiver alguma configuração inesperada, o count pode ser incorreto. Risco baixo — a política foi testada na Story 2.5.
- **Cliente sem acesso:** Placeholder já existe e será substituído — o estado vazio precisa ser mantido para clientes sem marcas atribuídas.

### Data Models

**`brands` table** [Source: docs/architecture/data-model-skeleton.md]:
```
id, slug, name, description (nullable), logo_url (nullable), published, owner_admin_id, created_at
```
RLS `brands_customer_read_published`: `published = true AND user_has_active_brand_access(brand_id)` — já filtra automaticamente.

**`products` table** [Source: docs/architecture/data-model-skeleton.md]:
```
id, brand_id, status (enum: extracted|approved|hidden), ...
```
RLS `products_customer_read`: `status = 'approved' AND user_has_active_brand_access(brand_id) AND marca.published = true`

O count embedded via PostgREST (`.select('brands.*, products(count)')`) usará automaticamente a RLS de `products`, retornando apenas a contagem de aprovados visíveis ao cliente — sem filtro explícito necessário.

### API Specification

**`getBrandsForCustomer()`** — nova Server Action em `lib/brands/actions.ts`:

```typescript
'use server'

export interface BrandForCustomer {
  id: string
  slug: string
  name: string
  description: string | null
  logo_url: string | null
  product_count: number
}

export async function getBrandsForCustomer(): Promise<BrandForCustomer[]> {
  const supabase = await createServerSupabaseClient()
  const { data, error } = await supabase
    .from('brands')
    .select('id, slug, name, description, logo_url, products(count)')
    .order('name', { ascending: true })
  if (error || !data) return []
  return data.map((b) => ({
    id: b.id,
    slug: b.slug,
    name: b.name,
    description: b.description,
    logo_url: b.logo_url,
    product_count: (b.products as unknown as [{ count: number }])?.[0]?.count ?? 0,
  }))
}
```

> [Source: docs/prd/6-epic-details.md#Story-3.5 + Supabase PostgREST embedded resources]

**Supabase PostgREST Embedded Count:**
`products(count)` retorna `[{ count: N }]` onde N é o número de linhas visíveis após RLS. A RLS `products_customer_read` limita a `status='approved'`, logo o count já é apenas de aprovados.
