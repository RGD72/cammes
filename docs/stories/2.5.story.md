## Story

**As a** dev fullstack,
**I want** um schema `products` completo com RLS refinada por `brand_id`, índices para a tela de revisão e testes de isolamento cross-brand,
**so that** a revisão e a vitrine subsequentes consultem rapidamente os produtos com isolamento garantido e sem vazamento cross-tenant.

## Acceptance Criteria

1. Tabela `products` possui todas as colunas definidas no PRD: `id`, `brand_id` (FK), `catalog_id` (FK), `reference`, `description`, `sizes` (jsonb array), `colors` (jsonb array), `price_brl` (numeric), `image_crop_url`, `look_group`, `source_page` (int), `extraction_confidence` (jsonb por campo), `status` (`extracted|approved|hidden`), `display_order` (int), `created_at`, `updated_at`.
2. Índices completos presentes: `(brand_id, status)`, `(brand_id, look_group)`, `(brand_id, display_order)`.
3. RLS refinada: política `products_customer_read` verifica `status = 'approved'` **E** marca tem `published = true` **E** existe `user_brand_access` ativa correspondente. Admin lê/escreve apenas produtos cujo `brand_id` pertença ao seu portfólio (política `products_admin_manage` existente mantida).
4. Migration de refinamento aplicada sem erros via `supabase db reset` (usa `CREATE INDEX IF NOT EXISTS` e `DROP POLICY IF EXISTS / CREATE POLICY`).
5. `docs/qa/rls-test-matrix.md` estendido com seção `products` documentando políticas, casos positivos e negativos.
6. Testes de integração em `tests/integration/rls/products.test.ts` cobrem: admin lê produtos da própria marca (positivo), admin não lê produtos de outra marca (negativo), customer lê produtos aprovados de marca publicada com acesso (positivo), customer não lê produtos não aprovados (negativo), customer não lê produtos de marca não publicada (negativo), customer sem `user_brand_access` não lê nada (negativo).

**O que falta (delta desta story):**

- Testes de integração RLS para `products`

### Política RLS Atual vs. Refinada

**Atual (`20260522000003_products_basic.sql:59-63`):**
```sql
CREATE POLICY products_customer_read ON public.products
  FOR SELECT USING (
    status = 'approved'
    AND public.user_has_active_brand_access(brand_id)
  );
```

**Refinada (deve substituir via DROP/CREATE):**
```sql
CREATE POLICY products_customer_read ON public.products
  FOR SELECT USING (
    status = 'approved'
    AND public.user_has_active_brand_access(brand_id)
    AND EXISTS (
      SELECT 1 FROM public.brands
      WHERE brands.id = products.brand_id
        AND brands.published = true
    )
  );
```

**Nota:** `user_has_active_brand_access(brand_id)` já existe como função helper RLS (criada em migration anterior). Verificar `supabase/migrations/20260521000001_rls_fix_infinite_recursion.sql` para a definição exata — a função usa `SECURITY DEFINER` e `SET search_path = ''`.

### Política Admin (mantida sem alteração)

```sql
CREATE POLICY products_admin_manage ON public.products
  FOR ALL USING (
    EXISTS (
      SELECT 1 FROM public.brands
      WHERE brands.id = products.brand_id
        AND brands.owner_admin_id = auth.uid()
    )
    AND public.current_user_is_admin()
  );
```

### Testes de Integração — Casos Obrigatórios

Baseado na estrutura de `tests/integration/rls/brands.test.ts` e `user-brand-access.test.ts`:

**Positivos:**
- `P-PR-1`: Admin_X SELECT produtos com `brand_id` pertencente ao Admin_X → retorna rows
- `P-PR-2`: Customer_A SELECT produtos `status='approved'` de marca `published=true` com `user_brand_access` ativa → retorna rows
- `P-PR-3`: Admin_X UPDATE produto de sua própria marca → afeta row

**Negativos:**
- `N-PR-1`: Admin_X SELECT produtos de marca de Admin_Y → 0 rows
- `N-PR-2`: Customer_A SELECT produtos `status='extracted'` (não aprovados) → 0 rows
- `N-PR-3`: Customer_A SELECT produtos de marca com `published=false` → 0 rows
- `N-PR-4`: Customer_A sem `user_brand_access` SELECT produtos de marca publicada → 0 rows

Reutilizar `rls-test-helpers.ts` para criação de fixtures (admin, customer, brand, user_brand_access).
