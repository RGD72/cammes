# Story 5.4 — Dashboard Inicial Admin (Métricas Básicas)

## Story Statement

**As a** admin-distribuidor,
**I want** um dashboard ao entrar em `/admin` com contagens-chave (marcas publicadas, produtos aprovados, pedidos do mês, custo OpenRouter do mês) e gráfico de pedidos por dia,
**so that** eu tenha visão imediata da operação sem precisar navegar por múltiplas telas.

## Status

Done

## Context

**Epic:** 5 — Admin Operations, Telemetry & LGPD Compliance
**Previous Story:** 5.3 — Gestão de Acessos: Convidar Cliente e Atribuir Marcas — Done
**Source:** `docs/prd/6-epic-details.md#story-54`

Stories 5.1–5.3 entregaram painel de pedidos, exportação CSV e gestão completa de clientes/acessos. Esta story transforma a landing page `/admin` (atualmente um placeholder com mensagem de boas-vindas, `app/admin/page.tsx`) em um dashboard real com KPIs, gráfico de pedidos e listas de atividade recente.

O `/admin` já existe como Server Component funcional (Story 1.5). A tarefa é substituir o conteúdo placeholder por dados reais, cacheados com `unstable_cache` (60s TTL) conforme especificado na arquitetura. `recharts` é a biblioteca de gráficos mandatada pela arquitetura (v2.13.x) — ainda não instalada no projeto.

O custo OpenRouter vem de `extraction_jobs.actual_cost_usd` + `actual_cost_brl` (sum do mês). A tabela `extraction_jobs` existe desde Story 2.x. A lógica de conversão BRL usa a coluna `fx_brl_usd` de `model_pricing` (ou env var `OPENROUTER_FX_BRL` como fallback com valor default 5.00).

### Caching Pattern (CRÍTICO)
`[Source: architecture.md#2.5 — Cache-Aside]`

```typescript
import { unstable_cache } from 'next/cache'

export const getAdminDashboardKpis = (adminId: string) =>
  unstable_cache(
    async () => {
      // queries here
    },
    ['kpis', adminId],
    { tags: [`kpis:admin:${adminId}`], revalidate: 60 }
  )()
```

**Nota:** `unstable_cache` wraps uma async function e retorna os dados cacheados. A tag permite invalidação manual via `revalidateTag('kpis:admin:' + adminId)` em mutações relevantes.

### RLS e Isolamento Multi-tenant
- `createServerSupabaseClient()` com session do admin aplica RLS automaticamente
- `brands` filtrada por `owner_admin_id = auth.uid()` via RLS → policy `brands_admin_full`
- `extraction_jobs` filtrados por `brand_id IN (admin_brands)` via RLS → policy `extraction_jobs_admin_full`
- `orders` filtrados por `brand_id IN (admin_brands)` via RLS → policy `orders_admin_own_brand`
- **Não usar service role para KPIs** — RLS do cliente regular é suficiente e mais seguro

### Query Approach para KPIs
A abordagem recomendada é:
1. Buscar brand IDs do admin via `supabase.from('brands').select('id').eq('owner_admin_id', adminId)` (RLS aplica)
2. Usar `.in('brand_id', brandIds)` nas demais tabelas
3. Alternativa: queries diretas com RLS ativo — Postgres filtra automaticamente. Preferir esta abordagem para simplicidade (menos queries)

Para contagem de pedidos por dia (série temporal 30 dias), usar raw SQL via `.rpc()` ou query com agregação:
```typescript
// Abordagem simples sem rpc:
const thirtyDaysAgo = new Date(Date.now() - 30 * 24 * 60 * 60 * 1000).toISOString()
const { data } = await supabase
  .from('orders')
  .select('submitted_at')
  .gte('submitted_at', thirtyDaysAgo)
// Agregar em JS: agrupar por date(submitted_at)
```

### Formato de Moeda
- BRL: `new Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' }).format(value)`
- USD: `new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(value)`

### Variação % (KPI Pedidos)
- `trend = ((ordersThisMonth - ordersLastMonth) / Math.max(ordersLastMonth, 1)) * 100`
- Exibir como: `+X%` (verde) ou `-X%` (vermelho) ou `N/A` se mês anterior for 0
