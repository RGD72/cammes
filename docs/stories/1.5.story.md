## Story

**As a** stakeholder do projeto,
**I want** ver que um admin autenticado entra em `/admin` com sidebar de navegação e seu nome exibido, e um cliente autenticado entra em `/brands` com header sticky e seu nome exibido,
**so that** toda a base de autenticação, redirecionamento por papel, exibição de dados de perfil e roteamento esteja comprovada antes de construir features reais.

## Acceptance Criteria

1. `/admin` renderiza layout com sidebar de navegação placeholder (links: Marcas, Pedidos, Configurações) e conteúdo principal com mensagem "Bem-vindo, [full_name do admin]", onde `[full_name]` é lido de `users_profile` via Server Component.
2. `/brands` renderiza header sticky com nome do cliente logado (`full_name` de `users_profile`) e conteúdo principal com mensagem "Você ainda não tem marcas disponíveis" — estado vazio amigável para Epic 3.
3. Middleware de Next.js já valida sessão em `/admin/*`, `/brands/*`, `/cart` e `/orders/*` (implementado na Story 1.3 — verificar que continua funcional; nenhuma alteração de middleware nesta story).
4. Layout admin usa sidebar lateral fixa (denso, adequado para desktop) implementada como `app/admin/layout.tsx`; layout cliente usa header sticky mobile-first implementado como `app/brands/layout.tsx`.
5. Documento `docs/qa/smoke-epic-1.md` criado com checklist manual cobrindo o fluxo completo do Epic 1: login admin, redirect, admin dashboard, logout → login customer, redirect, brands dashboard, logout, recover-password, reset-password.

## Risks

- **Fallback de `full_name` nulo:** usuários criados via Supabase CLI/Studio podem não ter `full_name` preenchido. O componente deve exibir um fallback (ex: "Admin" / "Usuário") — não pode quebrar se o campo for `null`.
- **Sidebar em mobile:** layout admin com sidebar lateral quebra em telas pequenas. Para o MVP, aceitar que `/admin` é desktop-only (documentado no smoke); link de "menu hamburguer" fica pós-MVP.

### Exibição de Nome do Usuário no Header do Cliente

AC2 exige o nome no *header sticky*. A abordagem correta para o Next.js App Router é tornar `app/brands/layout.tsx` um **Server Component** (já é por padrão — layouts são Server Components):

```typescript
// app/brands/layout.tsx — Server Component (lê perfil diretamente)
import { createServerSupabaseClient } from '@/lib/supabase/server'
import { LogoutButton } from '@/components/ui/logout-button'

export default async function BrandsLayout({ children }: { children: React.ReactNode }) {
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()

  const { data: profile } = user
    ? await supabase.from('users_profile').select('full_name').eq('id', user.id).single()
    : { data: null }

  const name = profile?.full_name ?? 'Usuário'

  return (
    <div className="min-h-screen bg-background">
      <header className="sticky top-0 z-10 border-b bg-background/95 backdrop-blur">
        <div className="flex items-center justify-between px-4 py-3">
          <span className="font-semibold">CAMMES</span>
          <div className="flex items-center gap-4">
            <span className="text-sm text-muted-foreground">{name}</span>
            <LogoutButton />
          </div>
        </div>
      </header>
      <main>{children}</main>
    </div>
  )
}
```

Desta forma `app/brands/page.tsx` **não precisa** buscar `full_name` — o layout já o exibe no header. A page.tsx foca apenas no estado vazio.

> **Nota:** Essa query duplica a leitura de `users_profile` que o middleware já faz, mas para o MVP é aceitável — a query é mínima (só `full_name`) e cacheada pelo Next.js Data Cache.
