## Story

**As a** dev fullstack,
**I want** tabelas `carts` e `cart_items` com RLS, e Server Actions para adicionar, editar quantidade, remover item, limpar carrinho e buscar carrinho,
**so that** o carrinho sobreviva a sessões e dispositivos do cliente, com isolamento garantido por marca.

## Acceptance Criteria

1. Tabela `carts` (id, user_id, brand_id, customer_name, created_at, updated_at) com UNIQUE (user_id, brand_id).
2. Tabela `cart_items` (id, cart_id, product_id, color, size, quantity, unit_price_brl_snapshot, total_brl, added_at).
3. RLS: usuário só vê/edita seus próprios carrinhos e cart_items; `addItem` verifica via Server Action que o produto pertence a uma marca com `user_brand_access` ativa do cliente.
4. Server Actions implementadas em `lib/carts/actions.ts`: `addItem` (substitui o stub da Story 4.1), `updateQuantity`, `removeItem`, `clearCart`, `getCart`.
5. Snapshot do preço (`unit_price_brl_snapshot`) capturado no momento da adição via leitura do campo `price_brl` do produto antes do INSERT.
6. NFR: operações de mutação <500ms p95 (índice em `cart_items(cart_id)` garante leitura eficiente).
7. Testes unitários: `addItem` com DB real mockado retorna `{ ok: true, data: CartItem }` (P-AI-1 completo); `getCart` retorna `{ ok: true, data: { cart, items, total } }`; `updateQuantity` e `removeItem` retornam resultados corretos; casos negativos cobrem auth, não encontrado e conflito.

## Complexity

**Médio** — 3 pontos

DDL simples (2 tabelas, 1 índice, 2 políticas RLS). O peso está em: (a) lógica UPSERT do carrinho (`ON CONFLICT DO UPDATE`) para garantir idempotência, (b) snapshot de preço via SELECT antes do INSERT, (c) 5 Server Actions com Zod e auth guard cada, (d) cobertura de testes unitários completa.

## Business Value

Sem este schema, o carrinho não persiste entre sessões e a Story 4.1 exibe apenas o modal (stub retornando INTERNAL). Esta story fecha o ciclo de persistência: cliente clica ESCOLHIDO → item entra no banco e sobrevive à troca de dispositivo ou refresh. É o pré-requisito direto de Story 4.3 (frontend do carrinho) e Story 4.4 (envio de pedido).

## Risks

- **UPSERT de cart com `ON CONFLICT`:** Precisa de `DO UPDATE SET updated_at = now()` para não ignorar silenciosamente o conflict. Se `DO NOTHING`, o `id` do cart pode não ser retornado — usar `RETURNING *` com a variante correta.
- **`total_brl` computed no INSERT:** O campo `total_brl = quantity * unit_price_brl_snapshot` deve ser calculado no Server Action e enviado no INSERT; não é computed column no Postgres (no MVP).
- **Recursão RLS:** As policies de `cart_items` usam subquery em `carts` — sem risco de ciclo pois `carts_owner` não referencia nenhuma outra tabela com RLS complexo.
- **P-AI-1 atualização:** O teste existente verifica `INTERNAL`; com a implementação real o mock precisa retornar insert OK para verificar `{ ok: true }`.

### Data Models

**`carts`** [Source: docs/architecture.md#4.7 + docs/architecture.md#DDL]:
```sql
CREATE TABLE carts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users_profile(id) ON DELETE CASCADE,
  brand_id UUID NOT NULL REFERENCES brands(id) ON DELETE CASCADE,
  customer_name TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, brand_id)
);
```

**`cart_items`** [Source: docs/architecture.md#4.7 + docs/architecture.md#DDL]:
```sql
CREATE TABLE cart_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  cart_id UUID NOT NULL REFERENCES carts(id) ON DELETE CASCADE,
  product_id UUID NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  color TEXT,
  size TEXT,
  quantity INTEGER NOT NULL CHECK (quantity >= 1 AND quantity <= 99),
  unit_price_brl_snapshot NUMERIC(10,2) NOT NULL,
  total_brl NUMERIC(12,2) NOT NULL,
  added_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_cart_items_cart ON cart_items(cart_id);
```

**TypeScript Interfaces** [Source: docs/architecture.md#4.7]:
```typescript
export interface Cart {
  id: string
  user_id: string
  brand_id: string
  customer_name: string
  created_at: string
  updated_at: string
}

export interface CartResult {
  cart: Cart
  items: CartItem[]
  total: number
}
```

### RLS Policies

[Source: docs/architecture.md#DDL + docs/architecture.md#section-decisões-rls]

```sql
ALTER TABLE carts ENABLE ROW LEVEL SECURITY;
ALTER TABLE cart_items ENABLE ROW LEVEL SECURITY;

-- Usuário só acessa seus próprios carrinhos
CREATE POLICY carts_owner ON carts
  FOR ALL USING (user_id = auth.uid());

-- Usuário só acessa cart_items do seu carrinho
CREATE POLICY cart_items_owner ON cart_items
  FOR ALL USING (
    EXISTS (
      SELECT 1 FROM carts c
      WHERE c.id = cart_items.cart_id
        AND c.user_id = auth.uid()
    )
  );
```

**Nota AC3 — `user_brand_access` guard:** A verificação de acesso à marca é feita no Server Action `addItem` via `user_has_active_brand_access(brandId)` (função SECURITY DEFINER já existente de `20260521000001_rls_fix_infinite_recursion.sql`), não via policy RLS separada. Arquitetura: [Source: docs/architecture.md#1075 — "gate RLS: user_brand_access existe" é o check no Server Action antes do UPSERT].

### API Specification

[Source: docs/architecture.md#5.1]

```typescript
// lib/carts/actions.ts — implementação completa (substitui stub)
'use server'

// --- addItem (substitui stub da Story 4.1) ---
// 1. auth.getUser() → PERMISSION_DENIED se não autenticado
// 2. AddItemSchema.safeParse(input) → VALIDATION_ERROR se inválido
// 3. user_has_active_brand_access(brandId) → PERMISSION_DENIED se sem acesso
// 4. SELECT price_brl FROM products WHERE id = productId (snapshot)
// 5. UPSERT INTO carts (user_id, brand_id, customer_name) ON CONFLICT (user_id, brand_id) DO UPDATE SET updated_at = now() RETURNING *
// 6. INSERT INTO cart_items (..., unit_price_brl_snapshot, total_brl) RETURNING *
addItem(input: AddItemInput) → Result<CartItem>

// --- getCart ---
// 1. auth.getUser() → PERMISSION_DENIED
// 2. SELECT carts WHERE user_id = auth.uid() AND brand_id = brandId → NOT_FOUND se não existe
// 3. SELECT cart_items JOIN products WHERE cart_id = cart.id ORDER BY added_at ASC
// 4. Calcular total = sum(item.total_brl)
getCart(brandId: string) → Result<CartResult>

// --- updateQuantity ---
// 1. auth.getUser() → PERMISSION_DENIED
// 2. UpdateQuantitySchema: { itemId: uuid, quantity: int.min(1).max(99) }
// 3. SELECT cart_items JOIN carts WHERE item.id = itemId AND carts.user_id = auth.uid() → NOT_FOUND
// 4. UPDATE cart_items SET quantity, total_brl = quantity * unit_price_brl_snapshot WHERE id = itemId RETURNING *
updateQuantity(input: { itemId: string; quantity: number }) → Result<CartItem>

// --- removeItem ---
// 1. auth.getUser() → PERMISSION_DENIED
// 2. SELECT para verificar propriedade (via RLS implícito — DELETE retorna 0 rows se não pertence)
// 3. DELETE FROM cart_items WHERE id = itemId (RLS garante isolamento)
// 4. Se count = 0 → NOT_FOUND
removeItem(itemId: string) → Result<void>

// --- clearCart ---
// 1. auth.getUser() → PERMISSION_DENIED
// 2. SELECT cart WHERE user_id = auth.uid() AND brand_id = brandId → NOT_FOUND se não existe
// 3. DELETE FROM cart_items WHERE cart_id = cart.id
clearCart(brandId: string) → Result<void>
```

**Nota sobre `customer_name` no UPSERT:** No MVP, `customer_name` é pré-preenchido com `users_profile.full_name` na criação do cart. O Server Action deve fazer SELECT do perfil antes do UPSERT.

### Technical Constraints

- **`'use server'`**: Todas as actions no mesmo arquivo já marcado
- **`createServerSupabaseClient`**: Já importado na Story 4.1; mantém o padrão
- **Mock pattern**: `vi.mock('@/lib/supabase/server', ...)` — mockar chain `.from().select()...`, `.from().insert()...`, etc.
