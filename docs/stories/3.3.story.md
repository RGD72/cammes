## Story

**As a** admin-distribuidor,
**I want** alternar a vitrine de uma marca entre `published` e `unpublished` com um toggle claro,
**so that** eu controle quando o cliente vê o catálogo finalizado e proteja coleções em revisão.

## Acceptance Criteria

1. Detalhe da marca (`/admin/brands/{id}`) expõe seção "Publicação da vitrine" com toggle "Publicar vitrine" e confirmação modal antes de publicar; modal exibe mensagem clara do que acontecerá e botões "Confirmar" / "Cancelar".
2. Toggle de publicação só habilita (não está disabled) se: existe ao menos 1 produto `status='approved'` E não há produtos `status='extracted'` pendentes; quando desabilitado, exibe tooltip ou texto explicativo com a razão.
3. RLS já existente (`brands_customer_read_published` + `products_customer_read`) reflete imediatamente após atualização de `published` — clientes só veem produtos de marcas `published=true`; esta story apenas garante que a Server Action atualize o campo corretamente.
4. Server Action `toggleBrandPublished(brandId, published)` valida server-side: ownership (`owner_admin_id = auth.uid()`), pré-condições de publicação (approved > 0, extracted === 0 quando `published=true`), atualiza `brands.published` e `brands.published_at` (ISO timestamp ao publicar, null ao despublicar), chama `logAuditEvent('brand_published' | 'brand_unpublished', { brandId })` e retorna `{ brand: Brand | null; error: string | null }`.
5. Despublicar é sempre permitido (sem validação de contagem de produtos) e não deleta produtos nem pedidos históricos.
6. Testes unitários: (a) `P-PUB-1`: `toggleBrandPublished` publica com sucesso quando approved > 0 e extracted === 0; (b) `N-PUB-1`: retorna erro quando há produtos `extracted` pendentes; (c) `N-PUB-2`: retorna erro quando não há produtos `approved`; (d) `P-UNPUB-1`: despublicação sempre bem-sucedida independente de contagens.

## Business Value

Sem este toggle, o admin não consegue controlar o momento de exposição do catálogo aos clientes — toda a vitrine ficaria sempre acessível ou nunca. Este é o mecanismo central que separa a fase de revisão da fase de publicação, respeitando o R3 do brief (isolamento por marca).

## Risks

- **RLS não atualiza imediatamente:** Supabase RLS é row-level e avaliada por query, então a mudança em `published` reflete na próxima query do cliente — sem cache adicional a invalidar no MVP.
- **Race condition publish/despublish:** Dois admins atualizando ao mesmo tempo é improvável no MVP (SaaS de distribuidor único por tenant), mas o ownership check e a transação atômica do Supabase mitigam.

### Server Action `toggleBrandPublished` — Padrão de Implementação

```typescript
// lib/brands/actions.ts
export async function toggleBrandPublished(
  brandId: string,
  published: boolean,
): Promise<BrandActionResult> {
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { brand: null, error: 'Usuário não autenticado.' }

  // Ownership check
  const { data: existing } = await supabase
    .from('brands')
    .select('id')
    .eq('id', brandId)
    .eq('owner_admin_id', user.id)
    .single()
  if (!existing) return { brand: null, error: 'Marca não encontrada ou acesso negado.' }

  // Pre-publish validation (apenas ao publicar)
  if (published) {
    const { count: extractedCount } = await supabase
      .from('products')
      .select('id', { count: 'exact', head: true })
      .eq('brand_id', brandId)
      .eq('status', 'extracted')
    if ((extractedCount ?? 0) > 0) {
      return { brand: null, error: 'Conclua a revisão dos produtos extraídos antes de publicar.' }
    }
    const { count: approvedCount } = await supabase
      .from('products')
      .select('id', { count: 'exact', head: true })
      .eq('brand_id', brandId)
      .eq('status', 'approved')
    if ((approvedCount ?? 0) === 0) {
      return { brand: null, error: 'Aprove ao menos 1 produto antes de publicar a vitrine.' }
    }
  }

  const { data: brand, error } = await supabase
    .from('brands')
    .update({
      published,
      published_at: published ? new Date().toISOString() : null,
      updated_at: new Date().toISOString(),
    })
    .eq('id', brandId)
    .eq('owner_admin_id', user.id)
    .select()
    .single()

  if (error) return { brand: null, error: error.message }

  await logAuditEvent(published ? 'brand_published' : 'brand_unpublished', {
    brandId,
    adminId: user.id,
  })

  return { brand: brand as Brand, error: null }
}
```

**Nota:** A validação server-side duplica a lógica de habilitação do botão no cliente (belt-and-suspenders). O cliente desabilita o botão; o servidor rejeita a requisição inválida caso o cliente seja contornado.
