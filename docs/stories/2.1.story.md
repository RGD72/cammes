## Story

**As a** admin-distribuidor,
**I want** cadastrar minha chave de API OpenRouter em uma tela dedicada, selecionar o modelo padrão, testá-la, vê-la sempre mascarada e atualizá-la a qualquer momento,
**so that** a plataforma possa usar minha chave para extração sem nunca a expor e eu mantenha controle do meu consumo.

## Acceptance Criteria

1. Tela `/admin/settings/openrouter` permite colar chave OpenRouter (input type password), selecionar modelo padrão (dropdown com modelos Vision do OpenRouter; pré-selecionado: `google/gemini-flash-2.5`) e botão "Testar conexão" que faz uma chamada mínima ao endpoint OpenRouter e retorna sucesso/falha visualmente.
2. Chave persistida na tabela `admin_settings` em coluna criptografada via `pgp_sym_encrypt` (pgcrypto, extensão já ativa) com chave-mãe na env var `OPENROUTER_KEY_ENCRYPTION_SECRET`; nunca armazenada em texto-claro.
3. Endpoint de leitura (`getOpenRouterStatus` Server Action) retorna sempre a chave mascarada (`sk-or-...XXXX` — apenas os últimos 4 caracteres visíveis), nunca em texto-claro.
4. Pipeline de extração (futuro) é bloqueado se a chave não estiver configurada — helper `getAdminOpenRouterKey(adminId)` retorna `null` se ausente; chamador lança erro descritivo.
5. Tela exibe o custo OpenRouter acumulado do mês corrente em USD e BRL (consultado via query em `extraction_jobs`); enquanto a tabela não existir, retorna R$ 0,00 graciosamente.
6. Salvamento da chave registra evento de auditoria `openrouter_key_updated` em `audit_logs` (tabela criada pela Story 5.5 — helper de auditoria deve ser no-op gracioso até lá).

## Complexity Estimate

**T-shirt size: M** (estimativa: 3–5 horas)

Razão: não há padrões arquiteturais novos para o projeto — segue o padrão de Server Components + Server Actions já estabelecido. O trabalho é: criar migration simples, Server Actions com pgcrypto via DB (não via Node — a criptografia é feita por query SQL), Client Component com formulário shadcn/ui, helper de teste de conexão HTTP, e testes unitários para a lógica de masking. O risco principal é a integração pgcrypto via `pgp_sym_encrypt` — testar localmente com Supabase.

## Business Value

FR7 + NFR8 + NFR12 — sem esta story, o pipeline de IA do Epic 2 (Stories 2.3–2.6) é inviável: não há como armazenar ou recuperar a chave OpenRouter com segurança. É o prerequisito bloqueador de toda a feature de extração, que é o core value proposition do CAMMES.

## Risks

- **pgcrypto via Server Action:** `pgp_sym_encrypt` / `pgp_sym_decrypt` são executados como queries SQL — o segredo (`OPENROUTER_KEY_ENCRYPTION_SECRET`) é passado como parâmetro à query. A env var NUNCA deve aparecer em logs de query. Usar parametrização SQL, jamais interpolação string. Mitigação: testes de regressão verificando que o segredo não vaza em mensagens de erro.
- **`OPENROUTER_KEY_ENCRYPTION_SECRET` ausente em produção:** pipeline falha silenciosamente ou lança erro criptográfico. Mitigação: validar env var na startup do Server Action; retornar erro descritivo ao admin se ausente.
- **OpenRouter API test endpoint — rate limit:** o teste de conexão consome quota da chave do admin. Usar endpoint leve (`/api/models` ou HEAD) em vez de completar uma geração. Mitigação: usar `/api/models` que não consome tokens.

### Decisão de Criptografia: pgcrypto vs Supabase Vault

**Escolha:** `pgcrypto` via `pgp_sym_encrypt` / `pgp_sym_decrypt` (simétrico, chave-mãe em env var).

**Rationale:** Supabase Vault requer configuração adicional de KMS e não está disponível em todos os tiers. `pgcrypto` já está ativo desde `20260520000001_extensions.sql`. A criptografia ocorre dentro do PostgreSQL — a chave-mãe é passada como parâmetro SQL parametrizado, nunca interpolada na string da query.

**Padrão de query (não interpolar a chave diretamente):**
```sql
-- CORRETO (parametrizado):
SELECT pgp_sym_encrypt($1, $2) AS encrypted
-- $1 = plaintext key, $2 = OPENROUTER_KEY_ENCRYPTION_SECRET

-- ERRADO (interpolação — NUNCA fazer):
SELECT pgp_sym_encrypt('${key}', '${secret}')
```
[Source: docs/prd/4-technical-assumptions.md — "Secrets management: Vercel Environment Variables para chaves de plataforma"]
