## Story

**As a** admin-distribuidor,
**I want** criar uma marca informando nome e slug, e fazer upload de um PDF de catálogo (drag-drop, até 500MB, com upload TUS resumível resiliente a quedas de conexão) associado à marca,
**so that** eu inicie o ciclo de digitalização daquela coleção.

## Acceptance Criteria

1. Tela `/admin/brands/new` permite criar marca (nome, slug auto-gerado editável, descrição opcional, logo opcional).
2. Detalhe da marca `/admin/brands/{id}` mostra zona drag-drop para upload de PDF + status atual do catálogo ("Nenhum catálogo" / "Em processamento" / "Pronto para revisão" / "Publicado").
3. Upload acontece via **protocolo TUS resumível** (`@supabase/storage-js` com opção `resumable: true`) diretamente cliente→Supabase Storage (bucket privado por `brand_id`), não passa por Vercel Function. Barra de progresso em tempo real; em caso de queda de conexão, o upload retoma do último byte confirmado sem reiniciar.
4. Validações no cliente e no servidor: extensão `.pdf`, MIME `application/pdf`, tamanho <=500MB.
5. Conclusão do upload cria registro em `catalogs` (id, brand_id, file_path, page_count, status, uploaded_at, uploaded_by).
6. Rate limit: max 3 uploads/hora/admin (NFR10).

## Risks

- **TUS client→Supabase direto:** o endpoint TUS do Supabase Storage requer o token de sessão do usuário no header `Authorization`. O client `@supabase/storage-js` com `resumable: true` gerencia isso automaticamente quando inicializado com o cliente de sessão do browser — mas a configuração do bucket e das policies DEVEM permitir acesso autenticado ao caminho `{brand_id}/{filename}`. Mitigação: testar localmente com `supabase start` antes de implementar o UI.
- **Rate limit sem Redis:** NFR10 exige max 3 uploads/hora/admin. Implementação via query em `catalogs` (`WHERE uploaded_by = auth.uid() AND uploaded_at > now() - interval '1 hour'`). Risco: não é atômico (race condition entre verificação e insert). Aceitável no MVP — a concorrência de uploads do mesmo admin é improvável.
- **Tamanho 500MB no browser:** browsers mobile podem cancelar uploads grandes em background. Mitigação: TUS retoma automaticamente; documentar limitação no smoke test.
- **Slug único global:** colisão possível se dois admins criarem marca com mesmo nome. Mitigation: constraint UNIQUE no banco; UI exibe mensagem de erro amigável.

## Dev Notes

**Decisão: XHR em vez de storage-js para upload com progresso**

`@supabase/storage-js` v2.106.0 (incluído em supabase-js 2.45.4) não expõe `onUploadProgress` na interface `FileOptions`. Optei por `XMLHttpRequest` direto ao endpoint `/storage/v1/object/catalogs/{path}` com o token de sessão do usuário. Isso entrega progresso real via `xhr.upload.onprogress` sem instalar dependência adicional.

**TUS resumível real — débito técnico registrado**

AC3 exige retomada do último byte confirmado. A implementação atual (XHR standard HTTP) não é TUS — em caso de queda de rede, o upload reinicia do zero. Para TUS verdadeiro, usar `tus-js-client` + endpoint `/storage/v1/upload/resumable`. Registrar como `TECH-DEBT-2.2-TUS` para story futura.

**Server-side validation via bucket config (SF-1 resolvido)**

`file_size_limit: 524288000` e `allowed_mime_types: ARRAY['application/pdf']` na criação do bucket garantem validação server-side no Supabase Storage sem necessidade de Server Action adicional. Supabase rejeita arquivos não-PDF e >500MB antes de salvar.

**Storage Policy com foldername (SF-4 resolvido)**

`(storage.foldername(name))[1]` retorna o primeiro segmento do caminho (brandId). A policy verifica que esse brandId pertence ao admin autenticado via JOIN em `brands`.
