# Story 5.6 — Consentimento LGPD no Cadastro e Política de Privacidade

## Story Statement

**As a** lojista-cliente cadastrando-se pela primeira vez,
**I want** aceitar explicitamente os termos de uso e a política de privacidade antes de concluir o cadastro,
**so that** a operação esteja em conformidade com a LGPD (base legal: consentimento + execução de contrato) e o registro de aceite seja auditável.

## Status

Done

## Context

**Epic:** 5 — Admin Operations, Telemetry & LGPD Compliance
**Previous Story:** 5.5 — Log de Auditoria e Eventos de Produto — Done
**Source:** `docs/prd/6-epic-details.md#story-56`

Story 5.3 entregou o fluxo de convite de clientes e adicionou um campo interim `terms_accepted_at TIMESTAMPTZ` em `users_profile` (migration `20260525000002_customers_terms.sql`). O formulário `app/invite/accept/_components/accept-invite-form.tsx` já exibe o checkbox "Li e aceito os Termos de Uso e a Política de Privacidade" com links para `/legal/terms` e `/legal/privacy` — mas essas páginas não existem ainda, e o registro de aceite não armazena a versão do documento nem o IP do cliente.

Story 5.5 entregou a tabela `audit_logs` real com `logAuditEvent()` funcional, que esta story usará para registrar `consent_accepted`.

A `data-model-skeleton.md` já documenta `consent_log` como tabela futura: _"consent_log, deletion_requests — pertencem aos Epics futuros"_.

Esta story substitui o mecanismo interim por:
1. Tabela `consent_log` (user_id, document_version, accepted_at, ip_address) — rastreamento versionado
2. Coluna `users_profile.consented_version TEXT NULL` em substituição a `terms_accepted_at` — lida pelo middleware numa única query eficiente
3. Constante `CURRENT_DOCUMENT_VERSION = '1.0'` — quando incrementada, força re-aceite automático via middleware
4. Páginas `/legal/terms` e `/legal/privacy` estáticas — conteúdo LGPD versão 1.0
5. Página `/consent/accept` — re-aceite para usuários existentes quando nova versão for publicada

CREATE TABLE consent_log (
  id          BIGSERIAL PRIMARY KEY,

### `recordConsent()` — Dois Clientes Supabase

```typescript
export async function recordConsent(documentVersion: string): Promise<Result<void>> {
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return permissionDenied()

  // service_role para INSERT (sem INSERT RLS user-facing em consent_log)
  const serviceSupabase = createServiceRoleSupabaseClient()

  let ipAddress: string | null = null
  try {
    const h = await headers()
    ipAddress = h.get('x-forwarded-for')?.split(',')[0]?.trim() ?? h.get('x-real-ip') ?? null
  } catch { /* headers() indisponível fora de request context */ }

  const { error } = await serviceSupabase.from('consent_log').insert({
    user_id: user.id,
    document_version: documentVersion,
    ip_address: ipAddress,
  })
  if (error) return internalError(error.message)

  // Atualizar cache no users_profile (lido pelo middleware)
  await supabase.from('users_profile')
    .update({ consented_version: documentVersion })
    .eq('id', user.id)

  await logAuditEvent('consent_accepted', { userId: user.id, documentVersion })
  return { ok: true, data: undefined }
}
```
