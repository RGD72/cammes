## Story

**As a** lojista-cliente,
**I want** clicar em "ENVIAR PEDIDO" no rodapé do carrinho, confirmar o resumo em modal, e ter o pedido salvo permanentemente com redirecionamento para tela de sucesso,
**so that** eu finalize minha intenção de compra e tenha um comprovante permanente acessível em qualquer dispositivo.

## Acceptance Criteria

1. Botão "ENVIAR PEDIDO" visível no rodapé da página `/cart/[brand_slug]`; ao clicar, abre modal de confirmação exibindo: número de itens (N), total geral (R$ X,XX) e botões "Confirmar" e "Cancelar".
2. Ao confirmar, Server Action `submitOrder(brandId, clientIdempotencyKey)` cria registro em `orders` (id, order_number `CMM-{YYYYMM}-{seq}`, brand_id, customer_user_id, customer_name, total_brl, status `received`, client_idempotency_key, submitted_at) e em `order_items` (snapshot completo das 8 colunas por linha de cart_item).
3. Após persistir, `cart_items` da marca são deletados (carrinho zerado); a row `carts` pode ser preservada vazia.
4. Um registro é inserido em `admin_notifications` (type `new_order`, order_id, brand_id, admin_user_id do dono da marca) — badge UI é Story 4.6.
5. Evento `order_submitted` é registrado em `audit_logs` com order_id e brand_id no payload.
6. Cliente é redirecionado para `/orders/{id}/success` com: número do pedido, total, botão "Baixar PDF" (desabilitado com tooltip "Gerando PDF..." — geração é Story 4.5) e link "Voltar à vitrine".
7. Tela `/orders/{id}` exibe detalhe read-only do pedido com tabela 8 colunas (REFERÊNCIA, DESCRIÇÃO DO PRODUTO, COR, TAMANHO, QUANTIDADE, NOME DO CLIENTE, VALOR DA PEÇA, VALOR TOTAL) e linha de Total Geral no rodapé.
8. Reenvio com mesmo `clientIdempotencyKey` retorna o pedido existente sem criar duplicata (idempotência).

```sql
CREATE TYPE order_status AS ENUM ('received','viewed');

CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_number TEXT NOT NULL UNIQUE,
  brand_id UUID NOT NULL REFERENCES brands(id),
  customer_user_id UUID NOT NULL REFERENCES users_profile(id),
  customer_name TEXT NOT NULL,
  total_brl NUMERIC(12,2) NOT NULL,
  status order_status NOT NULL DEFAULT 'received',
  client_idempotency_key UUID NOT NULL,

  UNIQUE (customer_user_id, client_idempotency_key)
);
CREATE INDEX idx_orders_brand_submitted ON orders(brand_id, submitted_at DESC);
CREATE INDEX idx_orders_customer ON orders(customer_user_id, submitted_at DESC);

CREATE TABLE order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id UUID REFERENCES products(id) ON DELETE SET NULL,
  reference TEXT NOT NULL,
  description TEXT NOT NULL,
  color TEXT,
  size TEXT,
  quantity INTEGER NOT NULL,
  customer_name TEXT NOT NULL,
  unit_price_brl NUMERIC(10,2) NOT NULL,
  total_brl NUMERIC(12,2) NOT NULL,
  display_order INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_order_items_order ON order_items(order_id);

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE order_items ENABLE ROW LEVEL SECURITY;

-- Cliente lê seus próprios pedidos
CREATE POLICY orders_customer_own ON orders
  FOR SELECT USING (customer_user_id = auth.uid());

-- INSERT via Server Action (autenticado, sem policy de INSERT user-facing — feito server-side)
-- Admin do dono da marca lê e escreve
CREATE POLICY orders_admin_own_brand ON orders
  FOR ALL USING (
    EXISTS (
      SELECT 1 FROM brands b
      WHERE b.id = orders.brand_id AND b.owner_admin_id = auth.uid()
    )
  );

-- order_items herdam acesso via order
CREATE POLICY order_items_inherit ON order_items
  FOR ALL USING (
    EXISTS (
      SELECT 1 FROM orders o
      WHERE o.id = order_items.order_id
        AND (o.customer_user_id = auth.uid()
             OR EXISTS (SELECT 1 FROM brands b WHERE b.id = o.brand_id AND b.owner_admin_id = auth.uid()))
    )
  );
```

**Nota:** INSERT de `orders` e `order_items` deve usar `createServerSupabaseClient` padrão (RLS ativa), não service role. O server-side do Server Action já garante que é o usuário autenticado inserindo.

### API / Server Actions

[Source: architecture.md#5.1]

**`lib/orders/actions.ts`** (novo arquivo):

```typescript
'use server'

import { z } from 'zod'
import { createServerSupabaseClient } from '@/lib/supabase/server'
import type { Result } from '@/lib/types'
import type { Order, OrderItem } from '@/lib/types'

// Helpers do padrão estabelecido em lib/carts/actions.ts:
// permissionDenied(), notFound(), internalError(), validationError()

const SubmitOrderSchema = z.object({
  brandId: z.string().uuid(),
  clientIdempotencyKey: z.string().uuid(),
})

export async function submitOrder(
  brandId: string,
  clientIdempotencyKey: string,
): Promise<Result<{ order: Order; items: OrderItem[] }>> {
  // 1. Auth guard
  // 2. Validação Zod
  // 3. Idempotência: verificar se order com mesmo (customer_user_id, client_idempotency_key) existe
  // 4. getCart(brandId) — se vazio, retornar NOT_FOUND
  // 5. Buscar owner_admin_id da marca para admin_notifications
  // 6. Calcular total_brl = sum(item.total_brl)
  // 7. Gerar order_number (CMM-{YYYYMM}-{seq}) via COUNT do mês corrente
  // 8. INSERT INTO orders
  // 9. INSERT INTO order_items (8 campos snapshot por item)
  // 10. DELETE FROM cart_items WHERE cart_id = cart.id
  // 11. INSERT INTO admin_notifications (type='new_order')
  // 12. logAuditEvent('order_submitted', { order_id, brand_id })
  // 13. return { ok: true, data: { order, items } }
}

export async function getOrder(
  orderId: string,
): Promise<Result<{ order: Order; items: OrderItem[] }>> {
  // 1. Auth guard
  // 2. SELECT orders WHERE id = orderId (RLS filtra: customer_own OU admin_own_brand)
  // 3. Se não encontrado → NOT_FOUND
  // 4. SELECT order_items WHERE order_id = orderId ORDER BY display_order
  // 5. return { ok: true, data: { order, items } }
}
```

**Notas críticas de implementação:**
- Não há transação real no Supabase JS client v2 — operações são sequenciais; em caso de falha após INSERT orders mas antes de INSERT order_items, o pedido ficará com 0 itens (estado inválido). Mitigação MVP: se INSERT order_items falhar, retornar INTERNAL e o cliente poderá retentar com o mesmo `clientIdempotencyKey` (a idempotência captura e devolve o pedido já existente, mesmo incompleto). Solução robusta é RPC/função PL/pgSQL (considerar para hardening pós-MVP).
- `generateOrderNumber`: `SELECT COUNT(*) FROM orders WHERE brand_id = $1 AND submitted_at >= date_trunc('month', now())` → seq = count + 1; formatar como `CMM-${year}${month.padStart(2,'0')}-${seq.toString().padStart(4,'0')}`.
- `admin_notifications.admin_user_id`: buscar via `SELECT owner_admin_id FROM brands WHERE id = brandId`.
- `logAuditEvent` de `lib/audit/log.ts` — se o arquivo não existir ainda, implementar helper mínimo inline que faz INSERT em `audit_logs` com `createServerSupabaseClient()`. Não usar service role para audit_logs (política INSERT é feita server-side via autenticação normal — os logs são inseridos sem policy user-facing, server action usa anon key com RLS, audit_logs não tem INSERT policy user-facing). **Alternativa segura:** usar service role client `lib/supabase/service-role.ts` apenas para o INSERT em `audit_logs` se RLS bloquear.
- Confirmação do modal: `clientIdempotencyKey = crypto.randomUUID()` gerado no client component quando o modal abre (não no clique de confirmar, para garantir estabilidade em re-renders).

### Decisions

1. **Service role para INSERTs em `orders`/`order_items`/`admin_notifications`**: Não existe policy de INSERT para usuários no schema. Usando `createServiceRoleSupabaseClient()` (já disponível em `lib/supabase/admin.ts`) para todas as operações de escrita. SELECT usa `createServerSupabaseClient()` (anon key + RLS). Solução segura: service role é chamado apenas em Server Actions, nunca exposto ao cliente.

2. **Modal nativo com Tailwind**: Radix UI não está instalado no projeto. Implementado `ConfirmOrderDialog` com overlay fixo e `role="dialog" aria-modal="true"` nativo — funcional e acessível sem dependências extras.

3. **`generateOrderNumber` usa `count: 'exact', head: true`**: Query de contagem mensal via Supabase `.select('id', { count: 'exact', head: true }).eq().gte()` — retorna apenas count sem dados. Evita `COUNT(*)` SQL explícito.

4. **`logAuditEvent` já existe como stub** em `lib/audit/log-event.ts` — usado diretamente sem implementar inline.

5. **`SubmitOrderSection` isolado do `page.tsx`**: `page.tsx` permanece RSC puro; `SubmitOrderSection` é o único Client Component, recebendo `brandId`, `itemCount`, `totalBrl` como props serializáveis.
