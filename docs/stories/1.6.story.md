## Story

**As a** engenheiro de qualidade,
**I want** uma matriz documentada de testes RLS positivos e negativos cobrindo as tabelas `brands` e `user_brand_access`,
**so that** qualquer regressão de isolamento entre marcas seja detectada imediatamente e o R3 do brief seja mitigado desde o Epic 1.

## Acceptance Criteria

1. `docs/qa/rls-test-matrix.md` documenta para cada tabela (`users_profile`, `brands`, `user_brand_access`): políticas RLS existentes, casos positivos (acesso permitido esperado) e casos negativos (acesso negado esperado) com resultado esperado explícito.
2. Suite de integration tests em `tests/integration/rls/` cobre, no mínimo: cliente_A não lê `brand_B` sem `user_brand_access` ativo; `admin_X` não lê brands de `admin_Y`; tentativa de UPDATE cross-tenant por admin errado falha; `uba_admin_manage` impede customer de inserir registros em `user_brand_access`; acesso revogado (`revoked_at IS NOT NULL`) é negado na policy `brands_customer_read_published`.
3. Testes de integração são executados por `npm run test:integration` e rodam no CI (`tests/integration/rls/` incluídos no pipeline); falha bloqueia merge.
4. `docs/architecture/project-decisions/ADR-002-rls-strategy.md` criado, documentando a decisão de usar Supabase RLS como camada exclusiva de isolamento multi-tenant, com rationale, consequências e referência à matriz.

## Complexity Estimate

**T-shirt size: M** (estimativa: 3–5 horas)

Razão: não há novos padrões arquiteturais — RLS já está implementado. O trabalho é: criar infrastructure de testes de integração (config vitest separada, fixtures de teste), escrever os testes que exercem as políticas RLS existentes, documentar a matriz e o ADR. O principal risco é o setup de CI com Supabase local.

## Business Value

R3 do Project Brief — vazamento cross-tenant de dados de marca — é o risco crítico mais alto do MVP. Esta story cria a rede de segurança: se qualquer refactor futuro enfraquecer uma política RLS, o CI bloqueia o merge antes do deploy. Sem esta story, confiamos exclusivamente na correção manual das políticas, sem detecção automática de regressão.

## Risks

- **CI com Supabase local:** o CI precisa de `supabase start` para rodar integration tests. O GitHub Actions Runner tem suporte, mas a configuração (Docker, porta 54321) pode falhar em ambientes restritivos. Mitigação: usar `SKIP_INTEGRATION_TESTS=true` como escape hatch documentado, mas o padrão é rodar.
- **Fixtures de teste com usuários reais:** criar usuários via `auth.admin.createUser` (service role) em testes deixa dados residuais se o teardown falhar. Mitigação: usar `afterAll` com cleanup explícito; prefixar e-mails com `test-rls-` para identificação.
- **Políticas com subquery em brands_customer_read_published:** a policy acessa `user_brand_access` com `revoked_at IS NULL`. Testar isso requer criação de fixtures em sequência específica (brand → access → revoke). Documentado nos testes.

### Padrão de Cliente para Testes RLS

Para testar RLS, é necessário um cliente com JWT de usuário real (não service role):

```typescript
// tests/integration/rls/rls-test-helpers.ts
import { createClient } from '@supabase/supabase-js'

const SUPABASE_URL = process.env.SUPABASE_URL ?? 'http://127.0.0.1:54321'
const SERVICE_ROLE_KEY = process.env.SUPABASE_SERVICE_ROLE_KEY ?? ''

export const supabaseAdmin = createClient(SUPABASE_URL, SERVICE_ROLE_KEY)

export async function getUserClient(email: string, password: string) {
  const client = createClient(SUPABASE_URL, process.env.SUPABASE_ANON_KEY ?? '')
  await client.auth.signInWithPassword({ email, password })
  return client
}

export async function createTestAdmin(emailPrefix: string) {
  const email = `${emailPrefix}-admin@test-rls.cammes.dev`
  const password = 'Test1234!'
  const { data } = await supabaseAdmin.auth.admin.createUser({
    email,
    password,
    email_confirm: true,
  })
  if (!data.user) throw new Error(`Failed to create admin user ${email}`)
  await supabaseAdmin.from('users_profile').insert({
    id: data.user.id,
    role: 'admin',
    full_name: `Admin ${emailPrefix}`,
    email,
  })
  return { id: data.user.id, email, password }
}
```

> **Nota:** Os valores default de `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` apontam para o Supabase local padrão (`supabase start`). Em CI, serão providos via env vars do GitHub Actions.

### Vitest: Config Separada para Integração

A config atual (`vitest.config.ts`) usa `environment: 'jsdom'` — inadequado para testes de banco. Criar config separada:

```typescript
// vitest.integration.config.ts
import { defineConfig } from 'vitest/config'
import { resolve } from 'node:path'

export default defineConfig({
  test: {
    environment: 'node',
    include: ['tests/integration/**/*.test.ts'],
    exclude: ['node_modules/**', '.next/**'],
    testTimeout: 30000, // queries de banco podem ser lentas
  },
  resolve: {
    alias: {
      '@': resolve(__dirname, '.'),
    },
  },
})
```

### Padrão de Cleanup de Fixtures

Usar `afterAll` com deleção via service role. E-mails prefixados com `test-rls-` para identificação e limpeza segura:

```typescript
afterAll(async () => {
  // Deletar via admin — ignora RLS
  await supabaseAdmin.from('user_brand_access').delete().in('user_id', [customerA.id, customerB.id])
  await supabaseAdmin.from('brands').delete().in('owner_admin_id', [adminA.id, adminB.id])
  await supabaseAdmin.auth.admin.deleteUser(adminA.id)
  await supabaseAdmin.auth.admin.deleteUser(adminB.id)
  await supabaseAdmin.auth.admin.deleteUser(customerA.id)
})
```

> **Nota:** A deleção em `auth.users` via `deleteUser` aciona `ON DELETE CASCADE` em `users_profile`. A ordem importa: deletar `user_brand_access` e `brands` antes dos usuários para evitar FK violations.

### CI — Supabase em GitHub Actions

O step de Supabase no CI segue o padrão oficial da Supabase CLI:

```yaml
- name: Setup Supabase CLI
  uses: supabase/setup-cli@v1
  with:
    version: latest

- name: Start Supabase local
  run: supabase start

- name: Run integration tests
  run: npm run test:integration
  env:
    SUPABASE_URL: http://127.0.0.1:54321
    SUPABASE_ANON_KEY: ${{ steps.supabase.outputs.anon_key }}
    SUPABASE_SERVICE_ROLE_KEY: ${{ steps.supabase.outputs.service_role_key }}
```

> **Nota:** `supabase start` aplica automaticamente todas as migrações em `supabase/migrations/`. Os dados de teste são isolados do ambiente de produção.
