## Story

**As a** admin-distribuidor,
**I want** agrupar produtos sob um mesmo LOOK e reordenar livremente a exibição da vitrine por drag-and-drop,
**so that** a vitrine respeite a curadoria visual da marca e a ordem editorial do catálogo original.

## Acceptance Criteria

1. Cada card na tela de revisão (`/admin/brands/{id}/review`) exibe o campo `look_group` com edição inline: input com autocomplete dos LOOKs já existentes na marca (via `<datalist>`) mais a opção de texto livre; ao confirmar (Enter ou blur), `updateProduct(productId, brandId, { look_group })` persiste; salvamento otimista com revert em erro e toast discreto.
2. A tela de revisão permite reordenar produtos por drag-and-drop (`@dnd-kit`); ao soltar um card em nova posição, a Server Action `updateProductsOrder(orderedIds, brandId)` persiste `display_order` em batch para todos os produtos da marca; toast "Ordem salva" confirma a operação; estado local reflete a nova ordem imediatamente (otimista).
3. Toggle "Agrupar por LOOK" na toolbar da tela de revisão alterna entre a view em grid flat (default) e a view colapsada por LOOK; no modo agrupado, cada grupo exibe cabeçalho com nome do LOOK e contagem de produtos, clicável para collapse/expand; produtos sem `look_group` aparecem em grupo "Sem LOOK" ao final.
4. Mudanças em `look_group` e `display_order` persistem imediatamente sem botão de salvar explícito; toast de confirmação ("LOOK atualizado" / "Ordem salva") é exibido após cada operação bem-sucedida.
5. Server Action `updateProductsOrder(orderedIds: string[], brandId: string)` valida que todos os IDs pertencem à marca do admin autenticado (pré-SELECT ownership check, mesmo padrão do `bulkUpdateProductStatus` da Story 3.1); atualiza `display_order` em batch (index-based: posição 0 = `display_order` 0, posição 1 = 1, etc.); retorna `{ updated: number; error: string | null }`.
6. Testes unitários: (a) `P-OR-1`: `updateProductsOrder` persiste `display_order` em batch e retorna `updated = N`; (b) `N-OR-1`: `updateProductsOrder` retorna erro se IDs não pertencem à marca.

## Scope

**IN:**
- Edição inline de `look_group` no `ProductCard` (combobox HTML5 nativo)
- Drag-and-drop para reordenação global de produtos na tela de revisão
- Vista "agrupado por LOOK" com collapse/expand
- Server Action `updateProductsOrder` com ownership check e batch update
- Extensão do tipo `data` em `updateProduct` para incluir `look_group`
- Testes unitários para `updateProductsOrder`

**OUT:**
- Edição de `sizes` e `colors` (arrays — não especificado para esta story)
- Reordenação dentro de grupos LOOK (a reordenação é global)
- Visualização agrupada na vitrine do cliente (Stories 3.4/3.5)
- Criação ou exclusão de grupos LOOK como entidades separadas

## Business Value

Admin pode organizar editorialmente o catálogo antes da publicação, respeitando a curadoria da marca (LOOKs). Reordenação drag-and-drop é a feature-chave que distingue a vitrine de uma exportação genérica de extração.

## Risks

- **DnD e touch:** `@dnd-kit` tem suporte a touch (mobile), mas testar em dispositivo real pode revelar edge cases de UX.
- **Batch update e race condition:** Drag rápido em sequência pode disparar múltiplos `updateProductsOrder`. Mitigar com debounce de 300ms antes de chamar a Server Action após soltar o card.
- **Catálogos grandes:** Para >200 produtos, o DOM do drag-and-drop pode ter impacto de performance. Documentar no Dev Notes — sem mitigação obrigatória no MVP (ARCH-001 da Story 3.1 já documenta esse limite).

### Server Action `updateProductsOrder`

Padrão de implementação (ownership check idêntico ao `bulkUpdateProductStatus` da Story 3.1):

```typescript
'use server'
export async function updateProductsOrder(
  orderedIds: string[],
  brandId: string,
): Promise<{ updated: number; error: string | null }> {
  if (orderedIds.length === 0) return { updated: 0, error: null }

  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { updated: 0, error: 'Usuário não autenticado.' }

  // Ownership check: todos os IDs pertencem à marca
  const { data: owned } = await supabase
    .from('products')
    .select('id')
    .in('id', orderedIds)
    .eq('brand_id', brandId)

  if (!owned || owned.length !== orderedIds.length) {
    return { updated: 0, error: 'Alguns produtos não pertencem a esta marca.' }
  }

  // Batch update: cada produto recebe seu novo display_order
  const now = new Date().toISOString()
  await Promise.all(
    orderedIds.map((id, index) =>
      supabase
        .from('products')
        .update({ display_order: index, updated_at: now })
        .eq('id', id)
        .eq('brand_id', brandId),
    ),
  )

  return { updated: orderedIds.length, error: null }
}
```

**Nota:** `Promise.all` com N updates individuais é aceitável para catálogos até 200 produtos (MVP). Para volumes maiores, considerar bulk update via RPC/SQL em sprint futuro.

### Drag-and-Drop com `@dnd-kit`

Padrão de integração mínima com `SortableContext`:

```typescript
// Em product-review-view.tsx (modo flat)
import { DndContext, DragEndEvent, closestCenter } from '@dnd-kit/core'
import { SortableContext, arrayMove, rectSortingStrategy } from '@dnd-kit/sortable'

// No JSX:
<DndContext collisionDetection={closestCenter} onDragEnd={handleDragEnd}>
  <SortableContext items={flatProducts.map(p => p.id)} strategy={rectSortingStrategy}>
    <div className="grid grid-cols-2 sm:grid-cols-3 lg:grid-cols-4 gap-4">
      {flatProducts.map(p => <SortableProductCard key={p.id} product={p} ... />)}
    </div>
  </SortableContext>
</DndContext>

// handleDragEnd com debounce:
const saveTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null)

function handleDragEnd(event: DragEndEvent) {
  const { active, over } = event
  if (!over || active.id === over.id) return

  setProducts(prev => {
    const oldIndex = prev.findIndex(p => p.id === active.id)
    const newIndex = prev.findIndex(p => p.id === over.id)
    return arrayMove(prev, oldIndex, newIndex)
  })

  if (saveTimerRef.current) clearTimeout(saveTimerRef.current)
  // IMPORTANTE: usar ref para capturar a ordem mais recente (evita closure stale)
  // currentOrderRef.current = newOrder (atualizar dentro do setProducts callback)
  saveTimerRef.current = setTimeout(() => {
    updateProductsOrder(currentOrderRef.current.map(p => p.id), brandId)
      .then(result => {
        if (result.error) { /* toast de erro + revert */ }
        else { /* toast "Ordem salva" */ }
      })
  }, 300)
}
```

### Decisão Técnica: `@dnd-kit` vs HTML5 DnD API

Usar `@dnd-kit` pelo suporte nativo a: teclado (acessibilidade), touch (mobile), sensors configuráveis e integração limpa com React 19. O bundle é pequeno (~7kb gzip para `core` + `sortable`). A API HTML5 nativa tem limitações de acessibilidade e eventos inconsistentes entre browsers.
