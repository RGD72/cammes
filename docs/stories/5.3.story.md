# Story 5.3 — Gestão de Acessos: Convidar Cliente e Atribuir Marcas

## Story Statement

As a **admin-distribuidor**,
I want **convidar um lojista por e-mail, atribuir-lhe acesso a marcas específicas e revogar acesso quando necessário**,
so that **eu controle quem vê quais coleções**.

## Status

InReview

## Context

**Epic:** 5 — Admin Operations, Telemetry & LGPD Compliance
**Previous Story:** 5.2 — Exportação de Pedidos em CSV — Done
**Source:** `docs/prd/6-epic-details.md#story-53`

Story 5.1 e 5.2 entregaram o painel de pedidos completo com exportação CSV. Esta story abre o ciclo operacional de onboarding de clientes: o admin-distribuidor deve poder convidar lojistas, associá-los a marcas e gerenciar o acesso. A tabela `user_brand_access` já existe (Story 1.2) com suporte a `revoked_at` para revogação soft. O convite usa a API `auth.admin.inviteUserByEmail` do Supabase (service role), que dispara um e-mail com link de cadastro.

O aceite explícito de termos LGPD no fluxo de cadastro (AC3) é a implementação mínima desta story — a Story 5.6 substituirá por `consent_log` com versionamento completo.

## Business Value

Fecha o ciclo de onboarding do MVP: sem esta story, o admin não consegue convidar clientes pela plataforma — é a funcionalidade que transforma a plataforma em multi-tenant operacional. Permite que o admin-distribuidor controle autonomamente quem acessa quais coleções, sem depender de intervenção técnica.

### Data Models

**users_profile** (existente — `supabase/migrations/20260520000010_users_profile.sql`):
```
id          UUID       PK + FK → auth.users(id)
role        user_role  'admin' | 'customer'
full_name   TEXT       Nome do cliente
email       TEXT       E-mail único
is_active   BOOLEAN    true = ativo; false = desativado (AC5)
created_at  TIMESTAMPTZ
updated_at  TIMESTAMPTZ
```
Nova coluna a adicionar: `terms_accepted_at TIMESTAMPTZ NULL` (AC3) via migration.

**user_brand_access** (existente — `supabase/migrations/20260520000030_user_brand_access.sql`):
```
user_id     UUID  PK + FK → users_profile(id)
brand_id    UUID  PK + FK → brands(id)
granted_at  TIMESTAMPTZ
granted_by  UUID  FK → users_profile(id)
revoked_at  TIMESTAMPTZ NULL  — NULL = ativo; preenchido = revogado
```

**Acesso ativo:** `revoked_at IS NULL`
**Revogar:** `UPDATE user_brand_access SET revoked_at = now() WHERE user_id = ? AND brand_id = ?`
**Reabrir acesso:** `UPDATE user_brand_access SET revoked_at = NULL, granted_at = now(), granted_by = ? WHERE user_id = ? AND brand_id = ?` — ou INSERT novo registro se não existir.

**RLS existente em `user_brand_access`:**
- `uba_admin_manage`: admin da marca pode fazer ALL
- `uba_self_read`: customer vê seus próprios registros

**Atenção:** Ao listar clientes do admin, filtrar por `brands.owner_admin_id = auth.uid()` para garantir isolamento multi-tenant.

### Supabase Admin API (Service Role)

```typescript
// lib/supabase/admin.ts — NUNCA exportar para client-side
import { createClient } from '@supabase/supabase-js'

export function createAdminSupabaseClient() {
  return createClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!,
    { auth: { autoRefreshToken: false, persistSession: false } }
  )
}
```

**Operações que requerem service role:**
- `adminClient.auth.admin.inviteUserByEmail(email, { data: { full_name }, redirectTo: '/invite/accept' })` — convite (AC2)
- `adminClient.auth.admin.listUsers()` — obter `last_sign_in_at` para AC1
- `adminClient.auth.admin.updateUserById(userId, { user_metadata: { ... } })` — opcional

**Segurança CRÍTICA:**
- `createAdminSupabaseClient()` SOMENTE em Server Actions e Route Handlers server-side
- NUNCA importar em Client Components ou arquivos com `'use client'`
- `SUPABASE_SERVICE_ROLE_KEY` NUNCA com prefixo `NEXT_PUBLIC_`

### Fluxo de Convite (AC2 + AC3)

```
Admin → modal "Convidar cliente" → Server Action inviteCustomer()
  → adminClient.auth.admin.inviteUserByEmail(email, { redirectTo: '/invite/accept' })
  → Cria users_profile (role='customer', is_active=true) se não existir
  → INSERT user_brand_access para cada brand selecionada
  → logAuditEvent('customer_invited', { email, brandIds })
  → Supabase envia e-mail com link

Cliente → clica link → /auth/callback?type=invite&token_hash=...
  → /invite/accept (via Next.js middleware redirect baseado em tipo de sessão)
  → Formulário: nova senha (required) + checkbox LGPD (required)
  → Server Action acceptInvite(password, termsAccepted)
    → supabase.auth.updateUser({ password })
    → supabase.from('users_profile').update({ terms_accepted_at: new Date().toISOString() })
    → redirect('/brands')
```

**Redirect de `/auth/callback` para `/invite/accept`:**
O callback route atual redireciona para `/brands` após troca de código. Para distinguir convites de magic links normais, checar `searchParams.get('type') === 'invite'` ou o estado da sessão (usuário sem `terms_accepted_at`).

Abordagem recomendada: middleware verifica `users_profile.terms_accepted_at IS NULL` após autenticação → redireciona para `/invite/accept` se for primeiro login de customer.

### Technical Constraints

- Supabase `auth.admin.inviteUserByEmail` disponível via REST Admin API — requer service role.
- `auth.admin.listUsers()` retorna dados de `auth.users`, incluindo `last_sign_in_at` — usar apenas server-side.
- Middleware em `middleware.ts` já intercepta rotas `/admin/*` e `/brands/*`; adicionar regra para `/invite/accept` (rota pública antes de autenticar, depois de aceitar).
- Para multi-select de marcas no modal: usar `<select multiple>` ou checkbox list (sem lib externa — consistente com o padrão existente no projeto de não adicionar dependências desnecessárias).
