# Story 5.7 — Direito ao Esquecimento (Exclusão de Conta sob Requisição)

## Story Statement

**As a** lojista-cliente,
**I want** solicitar a exclusão da minha conta e ter meus dados pessoais removidos em até 15 dias,
**so that** eu exerça meu direito previsto na LGPD (Art. 17, 18 e 20 da Lei 13.709/2018).

## Status

Done

## Context

**Epic:** 5 — Admin Operations, Telemetry & LGPD Compliance
**Previous Story:** 5.6 — Consentimento LGPD no Cadastro e Política de Privacidade — Done
**Source:** `docs/prd/6-epic-details.md#story-57`

Story 5.6 entregou o sistema de consentimento versionado com `consent_log` e as páginas legais. Esta story entrega o complemento LGPD obrigatório: o direito ao esquecimento (Art. 17-18 LGPD).

**Contexto técnico crítico:** `orders.customer_user_id` é definido como `ON DELETE RESTRICT NOT NULL` na migration `20260524000001_orders.sql`. Isso significa que não é possível deletar o registro de `auth.users` enquanto existirem pedidos vinculados — uma exclusão física quebraria a integridade referencial. A abordagem MVP é **anonimização de PII** (soft deletion): o registro de usuário persiste mas sem dados pessoais identificáveis, preservando a integridade contábil dos pedidos conforme exigido pelo AC4.

**Dados PII a remover:**
- `users_profile`: `full_name`, `email`, `phone`
- `auth.users`: email (via `supabase.auth.admin.updateUserById`)
- `orders.customer_name` e `order_items.customer_name`

**Email:** Nenhuma biblioteca de e-mail existe no projeto atualmente. Adicionar `resend` SDK como nova dependência para envio de e-mails transacionais (confirmação de solicitação e confirmação de conclusão). Variável `RESEND_API_KEY` como nova env var opcional — se ausente, os e-mails são silenciosamente ignorados (graceful degradation), mantendo a funcionalidade de exclusão funcional mesmo sem e-mail configurado.

`data-model-skeleton.md` já documenta `deletion_requests` como tabela futura: _"consent_log, deletion_requests — pertencem aos Epics futuros"_.

## Dev Notes

### BLOCKER CRÍTICO: `orders.customer_user_id ON DELETE RESTRICT`

`[Source: supabase/migrations/20260524000001_orders.sql]`

```sql
customer_user_id UUID NOT NULL REFERENCES public.users_profile(id) ON DELETE RESTRICT
```

**Implicação:** É impossível chamar `auth.admin.deleteUser(userId)` se o cliente tiver pedidos — a exclusão em cascata em `auth.users → users_profile` seria bloqueada pelo `ON DELETE RESTRICT` de `orders`.

**Solução MVP:** Anonimização de PII sem exclusão física:
1. UPDATE `users_profile` → dados anonimizados
2. UPDATE `orders`/`order_items` → `customer_name = 'Cliente removido'`
3. `auth.admin.updateUserById(userId, { email: 'removed-{uuid}@deleted.cammes', ban_duration: 'none' })` — desativa conta
4. **Não deletar** `auth.users` no MVP

**Phase 2:** Migration para `ON DELETE SET NULL` em `orders.customer_user_id` + hard deletion.

### Schema `deletion_requests`

`[Source: docs/architecture/data-model-skeleton.md — tabelas futuras Epic 5]`

```sql
CREATE TABLE deletion_requests (
  id             BIGSERIAL PRIMARY KEY,
  user_id        UUID NULL REFERENCES users_profile(id) ON DELETE SET NULL,
  user_email     TEXT NOT NULL,        -- preservado após anonimização para auditoria
  requested_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  status         TEXT NOT NULL DEFAULT 'pending'
                   CHECK (status IN ('pending', 'in_review', 'completed')),
  completed_at   TIMESTAMPTZ NULL,
  processed_by   UUID NULL REFERENCES users_profile(id) ON DELETE SET NULL,
  admin_notes    TEXT NULL
);
```

**Por que `user_id ON DELETE SET NULL`?** O registro de exclusão deve persistir como evidência de conformidade LGPD mesmo após o usuário ser anonimizado. `user_email` garante rastreabilidade.

**INSERT/UPDATE via service_role** — sem policy INSERT user-facing (mesmo padrão de `consent_log` e `audit_logs`).

### `executeAccountDeletion()` — Sequência de Operações

```typescript
// lib/deletion/actions.ts
export async function executeAccountDeletion(targetUserId: string): Promise<Result<void>> {
  // 1. Verificar que caller é admin
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return permissionDenied()
  const serviceSupabase = createServiceRoleSupabaseClient()
  const { data: callerProfile } = await serviceSupabase
    .from('users_profile').select('role').eq('id', user.id).single()
  if (callerProfile?.role !== 'admin') return permissionDenied('Apenas admins podem processar exclusões')

  // 2. Capturar e-mail do target ANTES da anonimização (para envio do email de conclusão)
  const { data: targetProfile } = await serviceSupabase
    .from('users_profile').select('email, full_name').eq('id', targetUserId).single()
  if (!targetProfile) return internalError('Perfil não encontrado')
  const savedEmail = targetProfile.email

  // 3. Anonimizar users_profile
  const anonymizedEmail = `removed-${targetUserId}@deleted.cammes`
  await serviceSupabase.from('users_profile').update({
    full_name: 'Conta removida',
    email: anonymizedEmail,
    phone: null,
    is_active: false,
  }).eq('id', targetUserId)

  // 4. Anonimizar orders.customer_name
  await serviceSupabase.from('orders')
    .update({ customer_name: 'Cliente removido' })
    .eq('customer_user_id', targetUserId)

  // 5. Anonimizar order_items.customer_name (via subquery em order_ids)
  const { data: orders } = await serviceSupabase
    .from('orders').select('id').eq('customer_user_id', targetUserId)
  if (orders?.length) {
    await serviceSupabase.from('order_items')
      .update({ customer_name: 'Cliente removido' })
      .in('order_id', orders.map(o => o.id))
  }

  // 6. Desativar auth user (não deletar — ON DELETE RESTRICT)
  await serviceSupabase.auth.admin.updateUserById(targetUserId, {
    email: anonymizedEmail,
    ban_duration: 'none',
  })

  // 7. Marcar deletion_request como completed
  await serviceSupabase.from('deletion_requests')
    .update({ status: 'completed', completed_at: new Date().toISOString(), processed_by: user.id })
    .eq('user_id', targetUserId)
    .eq('status', 'pending')

  // 8. Auditoria + e-mail (fire-and-forget)
  await logAuditEvent('account_deletion_completed', { targetUserId, processedBy: user.id })
  void sendEmail({ to: savedEmail, subject: 'Exclusão de conta processada', html: deletionCompletedEmail() })

  return { ok: true, data: undefined }
}
```

### Email: Wrapper Resend com Graceful Degradation

```typescript
// lib/email/send-email.ts
'use server'
import { Resend } from 'resend'

export async function sendEmail(params: {
  to: string
  subject: string
  html: string
}): Promise<{ ok: boolean }> {
  const apiKey = process.env.RESEND_API_KEY
  if (!apiKey) return { ok: false }  // graceful skip — não lança erro
  try {
    const resend = new Resend(apiKey)
    await resend.emails.send({
      from: process.env.RESEND_FROM_EMAIL ?? 'noreply@cammes.app',
      to: params.to,
      subject: params.subject,
      html: params.html,
    })
    return { ok: true }
  } catch {
    return { ok: false }  // falha silenciosa — email nunca bloqueia o fluxo principal
  }
}
```
