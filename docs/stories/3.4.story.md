## Story

**As a** lojista-cliente,
**I want** acessar a página da marca e ver todos os produtos em um grid responsivo, com busca textual, filtros por tamanho e por LOOK, e download do PDF original,
**so that** eu monte meu pedido com a mesma visualidade do catálogo original mas com agilidade digital.

## Acceptance Criteria

1. `/brands/{slug}` lista produtos `status='approved'` da marca `published=true` (RLS garante isolamento); se a marca não existir, não estiver publicada ou o cliente não tiver acesso, retorna 404.
2. Grid responsivo: 2 colunas em mobile, 3–4 colunas em desktop; imagens com lazy-load (`loading="lazy"`).
3. Cada card exibe: imagem (com fallback se ausente), referência, descrição curta (truncada em 2 linhas), preço formatado em BRL, badge de LOOK opcional (visível apenas quando `look_group` está preenchido).
4. Busca textual (debounced 300 ms) filtra client-side por referência ou descrição (case-insensitive).
5. Filtros client-side: por LOOK (select/chips de LOOKs distintos da marca) e por tamanho (multi-select de tamanhos disponíveis).
6. Botão "Baixar catálogo PDF" gera signed URL com TTL 5 min via Server Action e dispara download; exibe estado de loading enquanto gera.
7. Estado vazio amigável quando a busca/filtro não retorna resultados; estado separado quando a marca não tem produtos aprovados.
8. Página totalmente navegável por teclado: cards com `tabindex`, modal/filtros com foco gerenciado, sem traps de foco não-intencionais.
9. Testes unitários: (a) `P-GSB-1`: `getBrandBySlug` retorna marca quando slug válido e RLS permite; (b) `N-GSB-1`: retorna `null` quando marca não encontrada; (c) `P-PDF-1`: `getCatalogSignedUrl` retorna URL assinada; (d) `N-PDF-1`: retorna erro quando usuário não autenticado.

## Complexity

**Médio** — 3 pontos

Nova rota de cliente com Server Component + Client Component para interatividade (busca/filtros). A lógica de negócio é simples (RLS já cuida do isolamento); o esforço está no layout responsivo, debounce de busca e geração da signed URL.

## Business Value

Esta é a primeira tela que o cliente realmente usa no produto — sem ela, toda a extração e revisão do admin não têm saída. É o ponto de conversão do pipeline: catálogo PDF → vitrine digital navegável → pedido.

## Risks

- **Imagens ausentes:** `image_crop_url` pode ser null (extração não recortou); o fallback visual precisa ser gracioso.
- **Performance com muitos produtos:** grid de 100–200 itens com imagens pode ser lento. Lazy-load (`loading="lazy"`) e `display_order` já indexado mitigam.
- **RLS e acesso:** Se o cliente não tiver `user_brand_access` ativo, a query retorna zero resultados e `getBrandBySlug` retornará null → 404. Comportamento correto mas pode confundir o cliente em caso de acesso revogado (fora do escopo MVP).

### `getBrandBySlug` — Padrão de Implementação

```typescript
// lib/brands/actions.ts
export async function getBrandBySlug(slug: string): Promise<Brand | null> {
  const supabase = await createServerSupabaseClient()
  const { data, error } = await supabase
    .from('brands')
    .select('*')
    .eq('slug', slug)
    .single()
  if (error || !data) return null
  return data as Brand
}
```

**Nota RLS:** `brands_customer_read_published` garante que apenas marcas `published=true` com `user_brand_access` ativo são retornadas. Se a marca não existe ou o cliente não tem acesso, `data` será `null`. [Source: docs/architecture/data-model-skeleton.md#brands]

### `getCatalogSignedUrl` — Padrão de Implementação

```typescript
// lib/catalogs/actions.ts
export async function getCatalogSignedUrl(
  catalogId: string,
): Promise<{ url: string | null; error: string | null }> {
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { url: null, error: 'Usuário não autenticado.' }

  const { data: catalog, error: catError } = await supabase
    .from('catalogs')
    .select('file_path')
    .eq('id', catalogId)
    .single()
  if (catError || !catalog) return { url: null, error: 'Catálogo não encontrado.' }

  const { data: signedData, error: signError } = await supabase.storage
    .from('catalogs')
    .createSignedUrl(catalog.file_path, 300)
  if (signError || !signedData) return { url: null, error: 'Erro ao gerar link de download.' }

  return { url: signedData.signedUrl, error: null }
}
```

**Bucket:** `catalogs` (privado). TTL: 300 segundos = 5 minutos. [Source: components/admin/catalog-upload-zone.tsx:42]

### `getApprovedProductsForStorefront` — Separação de Admin/Cliente

```typescript
// lib/products/actions.ts — NOVA função (não modificar getProductsForReview)
export async function getApprovedProductsForStorefront(brandId: string): Promise<Product[]> {
  const supabase = await createServerSupabaseClient()
  const { data, error } = await supabase
    .from('products')
    .select('*')
    .eq('brand_id', brandId)
    .eq('status', 'approved')
    .order('display_order', { ascending: true, nullsFirst: false })
    .order('created_at', { ascending: true })
  if (error) return []
  return (data ?? []) as Product[]
}
```

**Nota:** `getProductsForReview` (admin) não filtra por status; esta nova função é exclusiva para vitrine (cliente). RLS `products_customer_read` garante acesso apenas a produtos approved de marcas published com acesso ativo.

### Decisão Técnica: Filtro Client-Side vs Server-Side

Filtro client-side foi escolhido porque:
1. Produtos aprovados de uma vitrine são O(50–200) no MVP — cabe em memória sem problema
2. Evita round-trips ao servidor para cada busca/filtro (UX mais rápida)
3. Debounce de 300ms + `useMemo` garante performance adequada
4. Consistente com a abordagem zero-latency do AC4 (debounced 300ms implica client-side)
